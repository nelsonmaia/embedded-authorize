## Overview

Embedded Authorize is a new authentication pipeline that enables native mobile and desktop SDKs  
to drive authentication entirely within the app, with no browser redirects and no WebViews. The  
server drives each step through `POST /e/authorize`, returning `next[]` actions the SDK renders,  
until a token is issued.

This document covers the **embedded signup** flow. The signup flow behavior is defined by the  
combination of identifiers and authentication methods configured in the connection. In this  
document we cover verifiable identifiers (**email** and **phone**), their corresponding  
authenticators (**email_otp** and **phone_otp**), and the collection of a **password**
authentication method after verifying the identifier (to avoid user enumeration). Each  
configuration is documented below as its own scenario, with the exact sequence of HTTP calls for  
its happy paths.

### How to read this document

This document has two main entrypoints:

* The [**Scenario index**](#Scenario-index) enumerates every signup scenario produced by the combination of factors and attributes that a database connection can be configured with. Use it when you want to understand the end-to-end behavior of a specific configuration: pick the row that matches the connection and follow its fully worked, self-contained sequence of HTTP calls.
* The [**Milestones**](#Milestones) section describes the order in which we will build those scenarios, sequenced to ship value as early as possible. Use it when you want to understand delivery: what is in scope for each increment and which scenarios it covers.

In short: the Scenario index answers "what does this configuration do?", and Milestones answers  
"when are we building it?".

Each scenario lists one or more **happy paths**, ordered from simplest to most complete:

1. **Happy path 1** completes only the required steps and skips every optional step. It is the minimum viable signup for that configuration.
2. **Happy path 2** completes the required steps plus the optional steps. It is still a happy path because completing optional steps is a must-have capability.
3. **Happy path N** completes further combinations of optional steps, where a scenario has more than one optional dimension.

**Alternate paths** (for example, removing an identifier before confirming) appear after the happy  
paths. They may or may not be in scope depending on how the work is broken down.

Each step is a single collapsible block containing both the request and the response. Expand the  
block to see the full JSON.

* M1 through M4 cover only the **happy paths** of their scenarios.
* M5 groups the alternate paths that are currently deferred, including identifier removal. Its scope will be defined once the removal design is settled.
* **Non-verifiable identifiers (username) are out of scope.** Signing up with a non-verifiable identifier such as username exposes user enumeration. Universal Login tolerates this risk because it has attack-protection measures (bot detection, suspicious IP detection, and others). Embedded Authorize does not yet have those protections, and its endpoint is easily scripted, so non-verifiable identifiers are deliberately excluded from the initial scope.

## Scenario 1: Email only, no password

### Description

A connection configured with a single identifier, email, required, and no password collection. The  
user provides an email address, proves ownership with an email OTP, and completes the signup. This  
is the simplest signup Embedded Authorize supports.

### Configuration

| Setting | Value |
| --- | --- |
| Attributes | email (required, identifier) |
| Phone | not enabled |
| Password | not collected |

### Happy path 1: required only

The only path for this scenario. Email is the sole required identifier, there are no optional  
steps, and no password is collected.

Steps:

1. Initiate the session.
2. Start the signup (`signup`), receiving the identifier menu.
3. Provide the email address (`identify:email`).
4. Send the email OTP (`challenge:email`).
5. Verify the OTP (`verify:otp`).
6. Confirm the signup (`signup:confirm`), receiving the authorization code.

```
POST /e/authorize
{
  "client_id": "clientId",
  "connection": "Username-Password-Authentication",
  "capabilities": [
    "action:signup:v1",
    "action:identify:email:v1",
    "action:challenge:email:v1",
    "action:verify:otp:v1",
    "action:signup:confirm:v1"
  ],
  "scope": "openid profile",
  "audience": "api_identifier"
}
```

Response:

```
{
  "error": "insufficient_authorization",
  "auth_session": "sess_1",
  "next": [
    { "action": "action:signup:v1" }
  ]
}
```

The client invokes the signup action returned by the initiate call. The server responds with the claim menu of allowed identifiers.

```

  "action": "action:signup:v1"
```

Response:

## Scenario 15: Email required, phone required, required password

### Description

The most complete mandatory configuration: two required identifiers (email and phone) and a  
required password. All three must be satisfied. `signup:confirm` is withheld until both identifiers  
are verified and the password is enrolled. There is a single happy path.

### Configuration

| Setting | Value |
| --- | --- |
| Attributes | email (required, identifier), phone (required, identifier) |
| Password | required |
